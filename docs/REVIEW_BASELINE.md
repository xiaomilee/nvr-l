## 一句话结论

> 最缺的不是功能，是把已有功能整合成**可信、能无人值守运行**的产品。

## 优先级分层（评审原文口径）

### P0 必须可靠的基础能力

| 功能 | 要补的东西 |
|---|---|
| 摄像头管理 | 连接测试、主辅码流、独立参数、批量操作 |
| 全时录像 | 断流检测、自动恢复、录像完整性检查 |
| 快照预览 | 显示最后成功时间、超时、错误原因 |
| 回放 | 时间定位、快速跳转、连续播放 |
| 存储管理 | 空间预警、保留策略、清理预览 |
| 系统诊断 | 一键导出完整诊断包 |

评审原话：**「我最看重的是录像可靠性。」**

每路必须有明确状态机，每次变化都要记下时间、摄像头、原/新状态、ffmpeg 退出码、
最近一次收到数据的时间、重连次数、故障原因、恢复耗时。并且——

> 不要只用 FFmpeg 进程是否存在来判断录像是否正常。
> 进程存在，不代表摄像头还有数据，也不代表录像文件还在正常增长。

### P1 最有价值的差异化（只两件）

1. **事件中心**：人员 / 车辆 / 两轮车 / 普通运动；按摄像头和时间过滤；前后录像；点击事件跳到录像时间点。
2. **智能缩时**：全时 / 活动 / 人员 / 车辆 / 多摄像头 / 按天摘要。

红线（原话）：**「检测漏报不能影响全时录像。录像是事实数据，检测只是对事实数据的解释。」**

### P2 增强型

Webhook（多模板、失败重试、发送历史）、模型版本管理与效果对比、GPU 自动探测与自动回退、
多区域配置、高级筛选、按时间范围批量导出。

### P3 明确不做

人脸识别、车牌识别、自定义模型训练平台、复杂多用户权限体系、过多实时滤镜。
理由不是没价值，而是模型依赖 / 硬件兼容 / 隐私 / 安全 / 维护成本远超收益。

## 评审点名的三个工程问题

1. **HTTP API 没有身份认证**。`X-NVR-Request` 只防 CSRF，不是凭证；服务要监听
   `0.0.0.0`（手机直连需求），所以不能靠改回 `127.0.0.1` 解决。建议安装级 `secret.json`
   + `Authorization: Bearer`，常量时间比对。
2. **事件定位靠前端拼文件名**。应以事件时间为唯一依据，服务端给 `{segment, offset_sec}`，
   并明确 `missing_reason`。
3. **检测与录像耦合**。检测要有界并发、绝不阻塞取帧与录像；失败要能看见（unknown ≠ 无活动）。

## 每轮开工前的三个自检问题

1. 这一轮做的事，落在上面哪一格？答不出来就说明方向偏了，回去看 ROADMAP 取活。
2. 会不会让「录像这条事实链」变得更不可信？（阻塞取帧、加长启动、增加失败点）
3. 有没有把 P3 的东西顺手做进来？做了就是超范围，写进「不在本轮范围」而不是悄悄合入。
